# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

zbCAD is a single-file, browser-based 2D CAD prototype (no server, no build dependencies, no npm). The entire application ships as one static HTML file with an inlined `<script>` IIFE containing all JS.

There are two parallel representations of the same program:

- `src/src/` — the real source, as ~59 ES modules (readable, one concern per file).
- `cad.html` (repo root) and `src/dist/cad.html` — the built single-file bundle. These two files are kept byte-identical; `cad.html` is the shippable artifact.
- `src/shell.html` — the HTML/CSS shell (head, body markup, styles) with an empty `(() => { })();` IIFE that the bundler fills with the concatenated modules.

**Always edit `src/src/**/*.js`, never edit `cad.html` or `src/dist/cad.html` directly** — they are generated. After editing source, rebuild (see Commands below).

## The build is a lossless, reversible concatenation

This is not webpack/esbuild/rollup — it's a small custom pair of scripts that trade generality for perfect reversibility:

- `src/tools/build.mjs` reads `src/src/.modules.json` (`order` = concatenation order), concatenates each module from `src/src/` in that order into `src/shell.html`'s IIFE, stripping `import` lines, stripping the `export` keyword, and re-indenting by two spaces. Each module is preceded by a `// path/to/file.js` banner comment.
- `src/tools/unbundle.py` does the exact inverse: given a hand-edited `dist/cad.html`, it re-derives the `src/` modules from the banner comments, and reconstructs each module's `import` statements by scanning its body for identifiers owned by other modules (via a computed symbol table). This lets someone hand-edit the bundled HTML directly and re-split it back into modules without retyping anything.
- `src/src/.modules.json` is the source of truth for module order plus a derived `owner`/`kinds` symbol table (which module declares which top-level `const`/`let`/`function`/`class`). It's regenerated by `unbundle.py` and validated by `graph.py` — don't hand-edit it unless you know what you're doing.
- `src/tools/graph.py` rebuilds the import graph from each module's own `import` lines, fails if there's a dependency cycle or if a module imports a name its target does not export, and reports unused imports. That export check matters because the bundle is one flat scope: a stale import still resolves there, so nothing but this check notices when the module graph stops describing the program.

Because of this design, module boundaries are a pure refactor of a single flat script — no bundler config, no tree-shaking, no dynamic imports.

## Commands

There is no `package.json`; everything runs via plain `node`/`python3`.

```sh
# Rebuild dist/cad.html from src/ and run static checks (cycle detection,
# unused imports, JS syntax check on every module) — the standard workflow
# after editing anything in src/src/:
sh src/tools/run-checks.sh

# Equivalent manual steps, if you need them individually:
python3 src/tools/graph.py          # validate import graph (cycles, unused imports)
node src/tools/build.mjs            # rebuild src/dist/cad.html from src/shell.html + src/src/
node --check src/src/path/to/file.js  # syntax-check a single module

# Regenerate src/ from a hand-edited dist bundle (rarely needed — only if
# someone edited the bundled HTML directly instead of src/src/):
python3 src/tools/unbundle.py <path-to-edited-cad.html> src
```

After `build.mjs` regenerates `src/dist/cad.html`, copy it to the repo-root `cad.html` (the two are meant to stay identical — the root copy is the one actually shipped/opened).

There is no lint command. Correctness is checked by `run-checks.sh` (structural checks), the headless suites below, and manual/in-browser verification.

```sh
# Drive the built bundle headlessly and assert behaviour. Run AFTER
# run-checks.sh — these test src/dist/cad.html, i.e. whatever was last built:
sh src/tools/tests/run-tests.sh

# Test a different bundle (e.g. the shipped root copy). The path is resolved
# from src/tools/tests/, which run-tests.sh cd's into, so pass an absolute one:
sh src/tools/tests/run-tests.sh "$PWD/cad.html"
```

`src/tools/tests/harness.mjs` boots the built single-file bundle inside a Node `vm` with a stubbed DOM, canvas and localStorage, and returns `window.__cadPrototype` (see `testHook.js`). Its `Image`/`FileReader` stubs resolve asynchronously, but they cannot decode anything: the image re-encode path is only meaningfully exercised in a real browser, so keep the pure parts (placement, calibration, transforms) callable with a plain descriptor. That hook exists precisely so the app can be driven and inspected without real DOM events. Prefer driving real commands (`startCommand`, `commitPoint`, `submitCommandText`) over seeding `state` directly, so a test exercises what a user's clicks actually produce.

**Test with realistic inputs, not just canonical ones.** Points that happen to land on a quadrant, an endpoint, or an axis take different code paths from the arbitrary points users actually produce with a NEAREST snap — a past associative-dimension bug survived a green suite for exactly this reason. Assert geometric *properties* (tangency, sweep, reflection) rather than only precomputed coordinates.

## Runtime architecture

The app has no framework and no build-time dependencies — plain DOM APIs, a `<canvas>`, and a global mutable `state` object (`src/src/state.js`). Module responsibilities, roughly bottom-up:

- **`dom.js`** — every DOM element lookup (`getElementById` etc.), done once, as named `const`s. Nothing else queries the DOM directly by id.
- **`core/`** — pure, side-effect-free helpers: geometric math (`math.js`), unit conversion/formatting (`units.js`), dimension-style defaults (`dimstyle.js`), constants and factory defaults (`constants.js`, `defaults.js`).
- **`state.js`** — the single mutable state object for the whole app (current drawing, mode, selection, view transform, active command's transient state, history stacks, etc.). `state.underlays` sits beside `state.entities` rather than inside it: an underlay is a raster with no geometry, and folding it in would mean a branch in every one of the seven-way type dispatches. Underlays share `state.selected` under the string id `u:<n>`, which cannot collide with an entity's integer id, so selection-filtering code needed no changes at all.
- **`model/`** — the document model: entities (`entity.js`), layers (`layers.js`, `layerQuery.js`), dimensions (`dimension.js`), undo/redo (`history.js`), save/load/autosave (`persistence.js`, `document.js`, `dirty.js`, `autosaveStore.js`). Autosave is **asynchronous**: the drawing lives in IndexedDB (`autosaveStore.js`), so `writeAutosave` and `restoreAutosave` return promises and recovery lands just after boot rather than during it. localStorage is left with one job — the snapshot `beforeunload` writes synchronously, because an IndexedDB transaction opened there is routinely aborted — plus the fallback when no database can be opened. Recovery reads both and takes the newer, which is what the sibling `.at` timestamp key is for.
- **`geometry/`** — pure geometry operations used by commands: trim/extend, offset, stretch, grips, edge editing, join/explode, affine transforms. `tangentCircle.js` holds the "every circle of radius R tangent to these two edges" construction, shared by FILLET and by CIRCLE's Ttr option; put anything else that answers the same question there rather than in a command.
- **`interaction/`** — turns raw input into domain actions: pointer/canvas hit-testing (`pointer.js`), typed command-line input parsing (`input.js`, e.g. `12<45` style point/distance/angle syntax), object snap (`snap.js`), ortho/polar tracking (`tracking.js`), selection (`selection.js`).
- **`commands/registry.js`** — the core abstraction of the app. A "command" (LINE, CIRCLE, TRIM, ROTATE, …) is a plain object with optional hooks (`begin`, `point`, `distance`, `keyword`, `prompt`, `preview`, `finish`, `close`, `undoPoint`, etc. — see the extensive comment block at the top of the file for the full contract) registered once via `defineCommand`. The dispatcher in this file is the *only* place that branches on which stage a command is in; individual commands never touch each other or duplicate that dispatch logic. **When adding a new drawing/editing command, follow this pattern rather than adding ad hoc mode-branching elsewhere.**
- **`commands/{draw,modify,transform,annotate,inquiry,aliases}.js`** — the actual command definitions, registered via `commands/registry.js`'s `defineCommand`/`registerDirectAction`, grouped by category. `aliases.js` maps short typed command names (e.g. `L`, `C`) to canonical ones.
- **`output/`** — writing the drawing out to a file for someone else to read. `plot.js` reduces the drawing to a *plot plan*: primitives measured in millimetres from the bottom-left of a sheet, Y up, with no knowledge of any file format. `pdf.js` serialises that plan into PDF operators (base-14 fonts only, deterministic output; the one embedded thing is an underlay image, written as `/Filter [/ASCII85Decode /DCTDecode]` so the PDF stays a pure-ASCII string and therefore stays assertable and safe to hand to `downloadTextFile`). `dxfPlan.js`/`dxf.js` are the same split for DXF, at a higher altitude — real ARCs, symbolic layer names and live DIMENSION entities rather than flattened line work. Keeping the plan separate from the writer is what lets a test assert that a hundred-foot line came out five inches long without parsing a PDF. **Any future export format should consume a plan-like intermediate the same way rather than walking `state.entities` itself** — and where there is also an importer, have it parse *into that same shape* (as `model/dxfRead.js` does), which is what makes a round trip assertable without going near the document model.
- **`view/`** — canvas rendering (`render.js`, `grid.js`), the world↔screen coordinate transform (`viewport.js`), and the render-scheduling handle (`frame.js`, the one deliberate indirection point: everything asks `frame.js` for a repaint, and `main.js` is what tells it what a repaint actually does, via `setFrameRenderer(render)`).
- **`events.js`** — a tiny pub/sub for "document changed" (used to trigger UI chrome refreshes like the layer panel, independent of rendering).
- **`ui/`** — non-canvas UI: the command-line prompt, status bar, layer panel, inquiry report panel, and modal dialogs (units, dimension style, snap/polar settings) under `ui/dialogs/`.
- **`main.js`** — the composition root. Every module is imported here purely for its side effects (commands self-register, UI/pointer modules attach DOM listeners); nothing else imports most of these modules directly. This is also where the app boots: wires the renderer, registers direct-action commands, restores autosave, and flips the engine status to READY.
- **`testHook.js`** — publishes `window.__cadPrototype`, a deliberately broad surface (raw state, pure helpers, and UI-triggering methods) that exists solely so an external headless test suite can drive and inspect the app without simulating real DOM events.

## Working conventions specific to this repo

- Modules use named ES `export`/`import` in `src/src/`; the bundler strips these mechanically, so don't introduce default exports, dynamic `import()`, or re-exports that the simple regex-based tooling in `build.mjs`/`unbundle.py`/`graph.py` can't parse (see the `IMPORT` regex in `graph.py` and the `DECL` regex in `unbundle.py` for exactly what's recognized). **An import must be one physical line** — `build.mjs` strips it line-by-line, so a wrapped `import {\n  a,\n} from './x.js';` survives into the bundle and breaks it at boot, which the static checks do not catch.
- Keep new top-level module symbols uniquely named across the whole codebase — `unbundle.py`'s ownership table assumes no two modules declare the same top-level identifier, and `graph.py`/`build.mjs` assume a flat, cycle-free `src/src/.modules.json` order. `graph.py` now **fails** on a duplicate, because nothing else catches one: the bundle is a single flat scope, so the later module silently wins while the import graph stays valid, every name still resolves, and `node --check` passes. Adding a new module means adding it to `order` in `src/src/.modules.json` in dependency order (after everything it imports).
- Comments in this codebase are used deliberately to explain *why* (e.g. the block comments in `main.js` and `commands/registry.js`) — match that style rather than narrating *what* the code does.
